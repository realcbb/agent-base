# 业务系统对接规范 v1（agent-base 网关契约）

本规范是业务后端与 AI 基座网关之间的对接契约，实现侧为 `gateway/`，
与《AgentScope 通用 AI 基座设计文档 v1.1》第 7 章一致；与本文冲突时
以本文为准（本文按已实现并冒烟验证的行为编写）。部署方法见 `DEPLOY.md`。

## 1. 接入前提

- 调用方只有**业务后端**。终端用户的页面/App 永不直连网关；页面需要
  的实时过程、确认卡都由业务后端订阅网关事件后转发/渲染。
- 每个业务系统是一个**租户**。接入时由基座运维在网关 `.env` 的
  `PROJECT_KEYS` 中为其分配 `租户名=随机密钥`，密钥只经安全渠道交付
  业务后端保管，不下发到前端。
- 网关地址：`http://<网关主机>:8000`，全部接口为 JSON（UTF-8）。
- **Java 系统可直接用官方 SDK**（随部署包 `sdk/java/`）：坐标
  `agentbase:agentbase-java-sdk:1.0.0`，JDK 17+、唯一依赖 Jackson。
  它封装了本规范的全部接口、事件流订阅（断线按序号补订）与确认
  回路（`Session.chat` 一站式），错误统一为带错误码与 traceId 的
  `GatewayException`。其他语言按本规范直调 HTTP 即可。

## 2. 通用约定

### 2.1 请求头

| 头 | 必填 | 说明 |
|---|---|---|
| `X-Project-Key` | 除 `/health` 外必填 | 租户密钥。缺失或错误返回 401 `AUTH_FAILED` |
| `X-End-User-Id` | 会话类接口必填 | 终端用户在业务系统内的唯一标识（如工号）。建会话时确定，同一会话后续所有调用必须同值，对不上按会话不存在处理。基座以 `{租户}:{终端用户}` 做资源隔离 |
| `X-End-User-Ts` | 断言校验开启时、凡带 `X-End-User-Id` 必填 | 秒级时间戳，网关容忍 ±300 秒 |
| `X-End-User-Proof` | 同上 | 终端身份断言：`HMAC_SHA256(项目密钥, "{终端用户}.{时间戳}")` 的十六进制串。项目密钥只有业务后端与网关持有——开启校验的部署（`GATEWAY_REQUIRE_USER_PROOF=1`）下，终端用户身份从"业务后端声称"升级为"可验真"：伪造工号或重放过期断言都会被 401 拒绝（`USER_PROOF_INVALID`/`USER_PROOF_EXPIRED`）。官方 Java SDK 内置断言生成（`endUserProof(true)`），裸 HTTP 对接按本行公式自算 |

### 2.2 标识

- `session_id`：32 位 hex，建会话时返回，会话全生命周期不变；
- `run_id`：`run-` 前缀，一次消息或一次确认续跑为一轮（run）；
- `event_id`：`evt-` 前缀，事件流断线续传的锚点（见 4.3）；
- `confirmation_id`：`cfm-` 前缀，待确认请求的标识（见第 5 节）。

### 2.3 错误信封

所有错误响应体统一为：

```json
{"code": "AUTH_FAILED", "message": "missing or invalid X-Project-Key", "trace_id": "…"}
```

`trace_id` 为本次请求的链路号，报障时提供。已实现的错误码：

| HTTP | code | 含义 |
|---|---|---|
| 401 | `AUTH_FAILED` | 租户密钥缺失或错误 |
| 401 | `USER_PROOF_INVALID` | 终端身份断言签名不符（断言校验开启时） |
| 401 | `USER_PROOF_EXPIRED` | 终端身份断言缺失或时间戳超出 ±300 秒 |
| 403 | `TENANT_FORBIDDEN` | 会话属于其他租户 |
| 404 | `AGENT_NOT_FOUND` | agent 不存在或不属于本租户 |
| 404 | `SESSION_NOT_FOUND` | 会话不存在/已归档/终端用户对不上 |
| 404 | `CONFIRMATION_EXPIRED` | 确认不存在或已被处理 |
| 409 | `SESSION_BUSY` | 同会话排队等待超过上限（默认 180 秒），稍后重试 |
| 429 | `QUOTA_EXCEEDED` | 触发限流：租户级（默认 120 次/分钟）或终端用户级（部署开启时），可配 |
| 400 | `MODEL_NO_VISION` | 消息带图片，但该 Agent 的模型名单里没有可用的识图模型（见 3.4） |
| 400 | `INTERNAL` | 参数不合法（如 mode、decision 取值错误） |

`MODEL_UNAVAILABLE`、`TOOL_DENIED`、`TOOL_TIMEOUT`、`RUN_LIMIT_EXCEEDED`
为预留码，当前实现不发出。

### 2.4 限流与并发

- 网关两级限流：租户级（默认 120 次/分钟，`GATEWAY_RATE_LIMIT_PER_MIN`；
  生产形态下为全租户全局口径，经多副本调用不倍增）与终端用户级
  （`GATEWAY_RATE_LIMIT_PER_USER_PER_MIN`，默认关，开启后单个工号
  独立分桶，不连累同租户其他人）；
- **同一会话同一时刻只跑一轮，新消息排队**：上一轮未收口时再发
  消息（或提交确认续跑），网关将其排队等前一轮收口，不会直接
  失败；等待超过 `GATEWAY_SESSION_QUEUE_TIMEOUT_SECS`（默认 180
  秒）返回 409 `SESSION_BUSY`，业务侧稍后重试即可。排队只在同一
  会话内成立，**不同会话之间互不影响、可并行**（含同一终端用户
  的多个会话；某会话挂起等确认不阻塞其他会话——等确认的会话
  本身不占队列，前一轮已收口）；
- 同步模式下一轮最长 120 秒（网关 `GATEWAY_RUN_TIMEOUT_SECS` 可调），
  超时该轮 `failed`。

## 3. 接口清单

### 3.1 健康检查

`GET /health`（免鉴权）→ `{"status": "ok", "model": "<当前模型名>"}`

### 3.2 列本租户可用 agent

`GET /v1/agents` →

```json
{"agents": [{"id": "demo.echo-assistant", "version": "1.0.0",
             "display_name": "…", "model": "…"}], "total": 1}
```

只返回本租户名下的 agent。

### 3.3 建会话

`POST /v1/sessions`，体：`{"agent_id": "<agent id>"}`，头带
`X-End-User-Id`。→ **201**：

```json
{"session_id": "…32hex…", "agent_id": "…", "tenant": "…", "end_user": "…"}
```

会话的历史由基座持久化，业务侧不需要、也无法直接读写历史原文。

### 3.4 发消息（双模式，见第 4 节）

`POST /v1/sessions/{session_id}/messages`，体：`{"text": "用户的话"}`，
查询参数 `mode=sync|async`（默认 sync）。

- sync → **200** 返回 run 记录（见 3.7），status 为终态；
- async → **202** 返回 `{"run_id": "…", "session_id": "…", "status": "running"}`，
  本轮转后台执行，过程与结果经事件接口获取（第 4 节）。

**图片输入（可选字段 `images`）**：`[{"url": "https://…", "media_type":
"image/png"}]` 或 `[{"data_base64": "…", "media_type": "image/png"}]`
（二选一；media_type 支持 png/jpeg/webp/gif；单条消息最多 8 张、
单张 base64 不超过约 14MB）。`text` 可为空但 text 与 images 不能同时
为空。**模型对业务侧透明**：用哪个模型由平台按 Agent 的登记策略
决定，业务侧不传、也不需要知道模型名；消息带图时平台会自动把会话
切到该 Agent 登记的识图模型（事件流里有 `model.switched` 可见痕迹），
会话历史含图后不会降回不识图的模型。若该 Agent 根本没登记识图
模型，带图消息直接回 **400 `MODEL_NO_VISION`**，不会静默吞图。

### 3.5 拉事件 / 订阅事件流

`GET /v1/sessions/{session_id}/events`，参数：

- `last_event_id`（可选）：只返回该事件之后的事件，用于增量拉取与
  断线续传；
- `stream`（可选，默认 false）：false 返回一次性 JSON
  `{"events": [ … ], "total": n}`；true 返回 **SSE 长连接**：先回放
  已缓冲事件，再实时推送新事件，15 秒无事件发一行 `: heartbeat`
  心跳注释。断线重连时带上最后收到的 `last_event_id` 即可续传，
  事件按 `event_id` 去重即可防重复投递。

事件结构与类型见第 6 节。

### 3.6 提交确认

`POST /v1/sessions/{session_id}/confirmations/{confirmation_id}`，
`mode` 参数同 3.4。请求体两种形状：

- **整批决定**：`{"decision": "approved|rejected|edited", "edited_input": "<可选>"}`，
  一个决定套给卡上全部工具调用。`edited` 表示"改了工具入参再批"，
  `edited_input` 为修改后的入参字符串；
- **逐调用决定**：`{"decisions": [{"tool_call_id": "…", "decision": "approved|rejected|edited", "edited_input": "<可选>", "rules": [<可选>]}]}`，
  一批工具调用里逐条表决（可批 A 拒 B）。`tool_call_id` 来自
  `confirmation.required` 事件的 `tool_calls[].id`；条目省略 id 且
  条数与调用数相等时按序匹配；未被条目覆盖的调用回落整批
  `decision`（可与 decisions 并存），再无则默认拒绝。条目的
  `rules` 为权限规则数组，网关不解释、原样透传框架（可用于
  "同类调用以后直接放行"这类记住选择，规则形状见框架权限
  规则定义）。

→ 返回续跑轮的 run 记录（sync）或 202 句柄（async）。确认被处理后
不可重复提交（404 `CONFIRMATION_EXPIRED`）。**确认没有有效期
倒计时**：会话挂起期间一直可确认；网关重启后待确认状态可自动
重建，不会丢。决定一经网关受理即记入确认台账与审计账（见 3.12），
与续跑执行结果无关。

### 3.7 查一轮运行

`GET /v1/runs/{run_id}` → run 记录：

```json
{"run_id": "run-…", "session_id": "…", "agent_id": "…",
 "agent_version": "…", "model": "…",
 "status": "running|awaiting_confirmation|completed|failed",
 "reply": "<completed 时为最终回复全文>", "ts": "…"}
```

run 在开轮时即登记，`running` 等在途状态可查——异步模式下业务侧
可用它做页面刷新后的状态对齐（常态进度走事件流，不必轮询它）。

### 3.8 关会话

`DELETE /v1/sessions/{session_id}` → `{"session_id": "…", "archived": true}`。
归档后该会话不可再用（404）。基座侧历史保留策略由基座运维定。

### 3.9 会话列表

`GET /v1/sessions`，请求头 `X-End-User-Id` 必填，可选参数
`agent_id` 限定某个 Agent → 该终端用户名下的会话（新→旧）：

```json
{"sessions": [{"session_id": "…", "agent_id": "…",
  "agent_version": "…", "name": "会话名（基座按首句生成）",
  "model": "…", "created_at": "…", "last_active_at": "…",
  "status": "…", "is_running": false}]}
```

用途：终端用户隔天回来、或业务后端重启后，按用户找回其
会话再取历史/续聊，业务侧不必自建会话索引。口径：列表由
基座会话存储直接供数（网关不自存会话索引），**已归档
（关闭）的会话不出现在列表里**；`status`/`is_running` 为
基座侧运行态。产品级标题、已读状态等仍是业务自己的数据，
`name` 只是基座自动生成的缺省名，可不用。

### 3.10 展示历史

`GET /v1/sessions/{session_id}/history` → 基座按会话投影出
可直接渲染的条目流（时间序）：

```json
{"session_id": "…", "items": [
  {"kind": "user", "text": "用户原文", "image": false, "ts": "…"},
  {"kind": "confirmation", "confirmation_id": "cfm-…",
   "tool_calls": [{"id": "…", "name": "…", "input": {}}],
   "impact": "…", "status": "pending|approved|rejected|edited|mixed",
   "ts": "…"},
  {"kind": "assistant", "text": "回复全文", "id": "消息 id",
   "run_id": "run-…（尽力关联）", "ts": "…"}]}
```

口径：**分工供数**——用户/助手正文取自基座持久化消息，
确认卡与决定取自网关确认台账（落库），两者按时间合并。
因此网关进程重启、运行态缓存丢失都不影响本投影的完整性，
业务侧无需自存会话历史。页面重开时取本接口渲染，再接
事件流看实时（两边按 run/确认编号去重）。未决确认卡
status=pending，恢复渲染后仍可经 3.6 提交决定；逐调用
决定过的卡 status 为 `mixed` 或统一决定值，逐条明细在
`decisions` 字段。边界：①确认台账自其启用时起记，启用
前已决定的卡不在历史中（正文不受影响）；②`run_id` 为
尽力关联（按回复文本对运行日志），对不上时只有消息 `id`；
③标题、已读状态等产品级展示数据不在投影内。

### 3.11 计量查询

`GET /v1/usage` → 本租户汇总：

```json
{"tenant": "…", "runs": 12, "input_tokens": 0, "output_tokens": 0,
 "token_source": "model_reported|none", "by_agent": {"<agent id>": 3}}
```

`runs` 口径为"产生过模型调用的轮数"。计量逐模型调用落库、跨网关
重启累计。当前计量库实现为演示级（见 `DEPLOY.md` 生产清单），数字
可作对账参考，正式计费口径以接入时约定为准。

### 3.12 审计查询

`GET /v1/audit`（租户级，可选参数 `limit`，默认 100、上限 500）
→ 本租户审计账（新→旧）：

```json
{"events": [{"ts": "…", "tenant": "…", "end_user": "…",
  "action": "session.created|session.archived|confirmation.decided",
  "session_id": "…", "ref_id": "cfm-…（确认决定时）",
  "detail": {"decision": "approved", "decisions": ["…"]}}]}
```

审计账是只追加的落库记录（独立于运行日志与事件流）：谁在
何时建/关了会话、对哪张确认卡做了什么决定，都可回查；
网关重启、运行态丢失不影响本账。业务侧自有审计（如确认卡
在页面上的呈现与点击）仍归业务侧记录，两边以
`confirmation_id`/`session_id` 对齐。

## 4. 调用模式（业务侧必读）

### 4.1 选型

| 场景 | 模式 |
|---|---|
| 面向人的页面/App（要展示思考过程、工具调用、确认卡、打字机增量） | **async**（默认推荐） |
| 服务端脚本、批处理、简单问答集成 | sync |

### 4.2 async 标准时序

```
业务后端                          网关
  │  POST messages?mode=async      │
  │ ─────────────────────────────▶ │  202 {run_id, status: running}
  │  GET events?stream=true        │
  │ ─────────────────────────────▶ │  SSE 长连接
  │        run.started             │
  │        message.delta（增量文本）│
  │        tool.calling / tool.result（工具过程）
  │        confirmation.required   │ ← 渲染确认卡，等用户决定
  │  POST confirmations/{id}?mode=async（用户点批准后）
  │ ─────────────────────────────▶ │  202 {run_id: 续跑轮}
  │        run.started（续跑轮）…   │
  │        run.completed           │ ← payload.reply 为最终回复
```

注意：确认卡对应的那一轮在 `confirmation.required` 后即以
`awaiting_confirmation` 收口（可经 3.7 查到），续跑是**新的一轮**
（新 run_id），不要把两轮混为一谈。

### 4.3 断线与恢复

- SSE 断线：带最后收到的 `event_id` 作 `last_event_id` 重连，先补
  回放再续实时，不丢事件；
- 页面刷新：用手头 `run_id` 调 3.7 对齐状态，再以 `last_event_id`
  （没有就全量）重拉 events 恢复界面；
- 业务后端进程重启：会话与历史在基座侧，不丢，重新订阅即可；
- 网关副本重启/切换：生产形态下事件与 run 记录存于共享状态后端，
  不丢；待确认可自动重建。在途轮次的执行不随副本迁移——执行
  副本死亡时该轮会被置为 `failed`（超时对账），业务侧按失败
  重试该条消息即可。

### 4.4 sync 时序（一句话）

POST messages（不带 mode）→ 网关阻塞至本轮收口 → 200 返回 run 记录；
若 status 为 `awaiting_confirmation`，业务侧从 events 接口取
`confirmation.required` 的 `confirmation_id` 与内容，呈现确认后调
3.6（sync）拿到续跑轮的终态记录。

## 5. 确认（HITL）约定

- 需要确认的是注册表里标为 **ASK** 级的工具调用（只读类为 ALLOW
  直行，DENY 级工具根本不会注册）。业务侧不需关心分级，只需处理
  `confirmation.required` 事件；
- 事件 payload 即确认卡的全部内容：`confirmation_id`、待执行工具
  列表 `tool_calls[].id/name/input`、影响说明 `impact`；
- 用户三种决定：`approved`（按原入参执行）、`rejected`（不执行，
  agent 会收到拒绝结果并继续本轮）、`edited`（用 `edited_input`
  替换入参后执行）；一张卡上有多个工具调用时可逐条表决
  （见 3.6 的逐调用形状），不必整批同进同退；
- 确认的呈现与收集是**业务界面**的职责，业务后端只做中继；基座不
  直连终端用户。审计分工：决定本身由网关审计账记录（见 3.12，
  含决定人、时间、逐条决定），业务侧记录卡片在自家页面上的
  呈现与操作上下文即可。

## 6. 事件类型表

事件统一结构：`{"event_id", "session_id", "run_id", "type", "ts", "payload"}`。

| type | 时机 | payload 要点 | 页面建议 |
|---|---|---|---|
| `run.started` | 一轮开始（含确认续跑轮） | `agent_id`，续跑轮另有 `resume_of`/`decision` | 显示"处理中" |
| `message.delta` | 回复文本增量 | `text` | 打字机追加渲染 |
| `tool.calling` | 工具调用开始 | `tool`（工具名）、`tool_call_id` | 过程条："正在调用 X" |
| `tool.result` | 工具调用结束 | `tool_call_id`、`state` | 过程条置完成/失败 |
| `confirmation.required` | 撞上 ASK 级工具 | `confirmation_id`、`tool_calls[{id, name, input}]`、`impact`、`created_at` | 渲染确认卡并暂停等待用户 |
| `model.switched` | 平台按策略给会话换了模型（如带图切到识图模型） | `from_entry`、`to_entry`、`model`、`reason` | 一般无需呈现；可作调试/审计线索 |
| `run.completed` | 一轮正常收口 | `reply`（最终回复全文） | 定稿渲染该轮回复 |
| `run.failed` | 一轮失败收口 | `{}`（细节查 run 记录与网关日志） | 呈现失败并允许重试 |

未列出的原生事件不翻译、不下发。事件语义只增不改：新类型可能随
版本增加，业务侧对未知 type 应忽略而非报错。

## 7. 版本与兼容

- 本规范为契约 **v1**。演进原则：只做加法（新接口、新字段、新事件
  类型），不改已有字段语义、不删接口；破坏性变更另发 v2 并双跑过渡；
- 业务侧应容忍响应中的未知字段；
- 网关实现与框架版本（AgentScope 2.0.11）对业务侧透明，基座升级
  不应影响本契约；若影响，视为基座缺陷。

## 8. 能力边界（明示，不必猜）

- **知识库（KB）**：平台级资产，不经契约接口管理。Agent 在注册表
  以名字声明 `knowledge_bases`，KB 本体由平台运营在租户系统户
  名下建好（建库与文档索引需要真实 embedding 凭证，演示用
  mock 凭证不具备 embedding 能力、建不了库）；网关建会话时
  按名解析并挂到会话上，同租户内经共享策略对终端用户只读
  可见。声明了却不存在的库名在网关侧有记录（kb_report），
  不静默生效也不报错阻断会话；
- **SOP**：不纳入契约。SOP 是平台运营资产：注册表定义由网关
  分发落库到租户系统户，框架层面终端用户本就不可见，业务
  系统无需也不应经契约读写 SOP；
- **组队（Team）与定时调度**：契约不暴露。业务侧的定时需求
  由业务后端自己的定时器到点调网关接口实现，不由模型侧
  工具触发；多 Agent 组队不在 v1 范围内；
- **终端身份的强度**：默认部署下 `X-End-User-Id` 由业务后端
  声称、网关凭项目密钥信任业务后端；开启断言校验（见 2.1）
  后升级为可验真。业务后端被攻破不在任何一种模式的防护
  范围内——项目密钥即租户边界，请按密钥规格保管。
